# Task 001: The per-card port interface

## Objective

Give every face a typed interface -- what it *is*, what it *installs*, what it
*consumes*, what it *produces* -- as an additive layer over the frozen graph, so
cards can be reasoned about as atomic units before anything is stitched together.

The existing card-pair projection is the *expansion* of this interface, not a
substitute for it. Bifur qualifies for Storied once; that single fact appears in
the graph as 74 incoming `CONTRIBUTES_TO_GATE` pair edges. The generator was
never made a first-class artifact, so the only way to ask "what does this card
offer, and what does it need?" is to walk the expansion backwards.

The distinction this card exists to draw: **a card installs a watcher; it does
not watch.** Bifur has the Storied ability, so it turns the enduring-story
watcher on. Smaug is a Legendary Creature and has no Storied text at all, yet
carries the identical `QUALIFIES_FOR gate:storied` edge -- provenance
`text: "Legendary Creature -- Dragon"`, `rule_ref: "mechanics article: Storied"`.
That edge is the watcher's inference materialised onto a card that knows nothing
about it. Smaug should expose `supertype:legendary` as a property and let the
watcher's own criterion match it.

## Acceptance Criteria

- [ ] `data/graph_global/watchers.jsonl` declares each watcher once with a machine-readable criterion. `storied` carries its threshold (three) and its qualifying predicate (artifact, legendary or Saga) as matchable data, not prose; `gate:storied` currently carries only `gate_type: distinct_object_threshold` and a label
- [ ] `data/graph_global/card_ports.jsonl` carries one record per face with `properties`, `installs`, `consumes`, `produces` and `unresolved`
- [ ] A card that installs a watcher references it by name and does **not** carry its criterion. The criterion has exactly one definition
- [ ] `QUALIFIES_FOR` is classified as watcher-derived and is never emitted as a card output. A test asserts Smaug's ports contain `supertype:legendary` under `properties` and no `storied` entry under `installs` or `produces`
- [ ] A test asserts Bifur installs `storied` and Smaug does not, derived from the same frozen graph
- [ ] Every ability node resolves to exactly one disposition: it causes an operation, installs a watcher, grants a keyword, or carries a recorded reason for none of those. The run reports the count in each disposition
- [ ] Bifur's third ability appears in `unresolved` with its clause text: it has an incoming `ENABLES` from `state:enduring_story` and no outgoing edge, so it is a declared dependency with no effect
- [ ] `SCALES_WITH` and `REQUIRES` are consumed, not produced. A test asserts Smaug's Treasure count reads as an input, since X is the number of artifacts opponents control
- [ ] Additive only: `nodes.jsonl`, `edges.jsonl` and `conditions.jsonl` are byte-identical after the run, and the frozen manifest is green
- [ ] Two serial runs produce byte-identical `card_ports.jsonl` and `watchers.jsonl`
- [ ] No card-name or UUID branches anywhere in the layer (repair-instructions acceptance gate 7)
- [ ] `hobkg ports` builds the layer and `hobkg query-ports "<card>"` prints one card's interface
- [ ] The implementer commits its own work with a readable trailer block carrying `Role: worker`, `Phase: ports-v1` and an `Iteration`, per INSTRUCTIONS.md section 8. The controller refuses to commit on the implementer's behalf and halts naming the SHA if the trailers are absent
- [ ] The commit leaves the working tree clean. `CONVERSATION_LOG.md` is appended by the session hooks and must be included, or verification refuses the tree it was asked to verify

## Requirements

- The layer **reads** the frozen graph. It does not re-extract from Oracle text, and it does not rewrite the frozen base -- follow the additive pattern the equip, completeness and lifecycle tiers already use
- Do not delete `QUALIFIES_FOR` edges. They are in the frozen artifacts. Classify them as watcher-derived and exclude them from card outputs
- An ability with no operation is recorded in `unresolved`, never dropped. The count of unresolved abilities is the headline number this layer exists to expose
- A keyword ability is a disposition, not an absence: `Flying` resolves as a keyword grant, not as an unresolved ability
- A watcher-installing ability legitimately causes no operation. Bifur's Storied ability must resolve as `installs`, not as `unresolved`
- Do not invent a port kind beyond the five. If a construct fits none of them, report that rather than widening the schema silently

## Notes

**The cycle phase is `ports-v1`, not `effect-4f`.** Every setup commit made on
2026-09-02 carries `Role: worker` and `Phase: effect-4f`, so
`GitRepo.awaiting_review(phase='effect-4f')` returns the newest of them and the
controller would resume against a task-card edit rather than running this work
item at all. A distinct phase keeps the setup commits out of this cycle's view
without rewriting any history.

**Amended before execution.** This card previously read "Classify every
unclassified census clause". That framing survived one conversation and was
replaced when the actual deliverable became clear: the per-card interface is the
goal, and the census is one way of measuring progress toward it rather than the
thing itself. The 82 unclassified clauses are still real -- they reappear here as
abilities that resolve to no disposition -- but "every clause has a family" is a
weaker acceptance criterion than "every ability has an operation, an install, a
keyword, or a reason", and it is not tied to anything anyone wants to query.

A prototype over the frozen edges, run 2026-09-02, already produces most of the
interface:

    Bifur, Melodic Rider
      properties    subtype:bard, subtype:dwarf, supertype:legendary, type:creature
      installs      storied
      consumes      ENABLED_BY state:enduring_story
      produces      ADDS_COUNTER counter:+1/+1
      derived       QUALIFIES_FOR gate:storied      <- watcher inference, not an output
      no-op         a1 (Storied: installs), a3 (Dwarf amplifier: genuine hole)

    Smaug, Wicked Worm
      properties    flying, subtype:dragon, supertype:legendary, type:creature
      installs      (none -- correct, Smaug has no Storied text)
      consumes      (should hold the artifact count; currently mis-filed)
      produces      CREATES_OBJECT token:treasure
      derived       QUALIFIES_FOR gate:storied      <- the misattribution, plainly
      no-op         a1 (Flying: keyword)

So the substrate carries most of what is needed and the work is largely
projection. The genuine gaps are the ones the prototype surfaces: abilities with
no operation, watcher criteria that are not machine-readable, and input/output
direction on `SCALES_WITH` and `REQUIRES`.

The build spec's own words support the direction: higher-order gates are to be
"represented without combinatorial enumeration". Seventy-four pair edges standing
in for one property match is the enumeration it warns against.
