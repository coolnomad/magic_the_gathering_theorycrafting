# Task 008: Apply the phase-1 operator decisions and re-freeze the dataset

## Objective

Section 7 of `reports/benchmark_phase1_audit.md` put two questions to the
operator. Both are now answered, and this card applies them.

**One.** The 166 observations with no historical win-rate bucket are excluded
from the modeling population. They cannot be scored by R0, whose only feature is
`base_p`, so an exclusion was always coming; the operator's decision is that it
lands here rather than being carried further. Measured before deciding: those
166 games belong to 59 drafts, and **all 59 are entirely null** -- zero drafts
are partially affected -- so excluding games and excluding drafts are the same
operation and no tie-breaking rule is needed.

**Two.** The games-played buckets are taken from what the data contains, not
declared up front. The inherited `hist_w` map carries a `1000` key that never
occurs in this dataset. Stop referencing it.

Everything downstream of the population definition is re-derived, not patched.
The split is **recomputed**, not filtered, because a filtered split would leave
the holdout fraction and the fold sizes subtly wrong on the smaller population.

## Notes

**The numbers this card expects, and where they came from.** Measured directly
from the raw CSV on 2026-09-08, before the decision was taken: 166 games carry
an empty `user_game_win_rate_bucket`; they belong to 59 drafts; **all 59 are
entirely null and none is partially null**; and no row anywhere in the file has
a missing games-played bucket. The population therefore goes from 241,727 games
across 43,161 drafts to 241,561 across 43,102. These are stated so a mismatch is
visible, not so they can be typed into the code.

**Why the split is recomputed rather than filtered.** Removing 59 drafts moves
the 20th-percentile time boundary slightly and unbalances the five folds. A
filtered split would still satisfy "no draft in both partitions" while quietly
holding out something other than 20 percent, and the fold sizes would drift
apart. Recomputation costs nothing here because the split is a deterministic
function of the population and a declared seed.

**Why the carve-out is deleted rather than left in place.** Card 005 permitted a
structurally-absent win-rate bucket as a counted null, because failing on it
would have made that card's own output validation unsatisfiable. With those rows
gone from the population the branch is unreachable, and unreachable safety
behaviour is worse than none: it looks like a guard, it is never exercised, and
the next person to read it will assume nulls are expected. Deleting it restores
the original intent of card 005's criterion 8 -- any null in the population is a
defect and stops the run.

**On deriving the bucket set.** The buckets present in this file are
`{1, 5, 10, 50, 100, 500}`. What is derived from the data is *which buckets
exist*; the weight attached to each is a modeling assumption inherited from the
R implementation and is not derivable from this dataset. Both facts should be
legible in the code: an observed set, and a declared weighting over it. A bucket
that appears in the data with no declared weight is an error and must stop the
run rather than be interpolated -- that rule is unchanged from card 005 and is
the reason the `1000` entry was harmless, merely untested.

**What this card does not do.** It does not begin Phase 2, fit anything, or open
the holdout. It re-freezes the phase-1 dataset under the operator's decisions so
that Phase 2 inherits one coherent population with no null-handling policy to
invent.

**Why the heavy commands are Checks and not Output Validation.** Compact applies
two different timeouts: `DEFAULT_CHECK_TIMEOUT_SECONDS = 300` for checks, and
`DEFAULT_VALIDATION_TIMEOUT_SECONDS = 60` for output validation. Neither is
documented in `GUIDE.md`. The first attempt at this card put
`python -m pytest tests/ -q` in Output Validation, where it was killed at 60.1
seconds and the task went to BLOCKED -- even though the same suite passes in
about 188 seconds, and the task-level Checks command passed at 73.6 seconds
under the larger cap. The executor's work was complete and every command exited
zero; only the placement was wrong.

Measured on 2026-09-08 against the 60-second cap: full suite 187.8s, the
five-file targeted suite 70.7s, `deckbench.identity` 45.0s, `deckbench.table`
25.9s, everything else under 4s. So the derivations that re-read the 16 MB gzip
belong in Checks, and Output Validation keeps the fast decisive assertions.
Nothing is lost -- both sections must pass for the task to advance -- and the
full suite still runs as the inherited registry default check, which is why this
card no longer skips it.

A related trap: a validation timeout is serialized into the audit entry as
`exit code 0`, because `TimeoutExpired` leaves `exit_code` unset and the header
renders the missing value as zero. A FAIL line reading "exit code 0" means the
command was killed, not that it succeeded.
