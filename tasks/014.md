# Task 014: Compute mu per draft, as the proxy being reproduced does

## Objective

`mu`, the shrinkage target in the skill proxy, is currently the mean of
`base_p_raw` over **games**. The R implementation this proxy reproduces computes
it over **drafts**. Change ours to match, and carry the change through
everything that depends on it.

Section 3 of the benchmark is explicit that the proxy is reproduced rather than
improved, so that the representation experiment is isolated from changes in
skill estimation. A per-game `mu` is not the proxy the earlier work used, so the
current implementation quietly fails that requirement.

## Acceptance Criteria

- [ ] `mu` is computed as the mean of `base_p_raw` over **distinct drafts**, one value per draft, not over game rows
- [ ] The report records both values — the per-game `mu` this replaces and the per-draft `mu` that replaces it — and states which the R implementation uses, citing the file and line
- [ ] The estimation population is otherwise unchanged: the same 43,102 drafts and 241,561 games as card 008 froze, with no row added, dropped or reweighted
- [ ] A test asserts `mu` is invariant to how many games a draft contributes, by constructing a fixture where one draft has many games and another has one, and checking the result equals the unweighted mean of the two drafts' values
- [ ] `data/processed/skill_features.parquet` is re-emitted; `base_p_raw` is unchanged for every row and only `base_p` moves
- [ ] `data/runs/T0_R0*` and `data/runs/T0_R1*` are **refitted**, because R0 is `[base_p]` and R1 contains it, so card 011's fits are stale the moment `mu` changes
- [ ] Refitting goes through `deckbench.estimator.fit_and_predict` unchanged, with the same seed and the same frozen split; a run record is written for each and the split SHA256 in it still matches `split_manifest.json`

## Notes

**The measurement that justifies this card**, taken 2026-09-09 on the frozen
population:

    mu, per game  (current)      0.546211
    mu, per draft (R original)   0.533339
    difference                  +0.012872

They differ because stronger players play more games. The 7-wins/3-losses
structure means a good run is ten games and a bad one is three; measured
mean games per draft rises from about 2.5 in the lowest historical win-rate
bucket to roughly 6.5-7.5 in the 0.66-0.86 buckets. Averaging over games
therefore over-samples strong players and pulls the shrinkage target upward.

**The bias lands where the proxy does the most work.** `mu` only matters when
`hist_w` is small, which is exactly the new players the shrinkage exists to
protect. Measured effect on `base_p` of the two `mu` values:

    hist_w =  1   +0.0108
    hist_w =  2   +0.0092
    hist_w =  3   +0.0080
    hist_w =  6   +0.0057
    hist_w =  8   +0.0047
    hist_w = 12   +0.0035

So a player with one game of history is currently credited with about a
percentage point more than the reproduced proxy would give them, and a
seasoned player about a third of that.

**Why now rather than later.** T1 is defined as the bump against this specific
baseline and T2 as the bump against a learned one; the whole point of that axis
is that the baselines differ in a controlled way. If `mu` changes after T1 and
T2 are fitted, both are void and the comparison between them means nothing. The
cost today is one re-emission and two refits. The cost after T2 is every fit in
the phase.

**The cascade is wider than the skill table.** R0 is `[base_p]` and R1 is
`base_p` plus the card fractions, so card 011's `T0_R0` and `T0_R1` both consume
the changed column and are stale as soon as it moves. They are refitted here.
`model_table.parquet`, `deck_identity.parquet` and `model_split.parquet` do not
depend on `base_p` and must not change; the split in particular is keyed on
`draft_id` and time, so its hash should be identical afterwards.

**Honest scale of the effect.** 0.0129 on the shrinkage target, and at most
about 0.011 on any individual `base_p`. This is a fidelity correction, not a
discovery, and the report must say so. The argument for making it is that the
benchmark asked for a reproduction and this is not one — not that the numbers
are badly wrong.

**Why the first run FAILED review, and the card-design flaw behind it.** The
reviewer found `reports/benchmark_phase1_audit.md` pinning
`skill_features.parquet` at `fea8a062...` while `MANIFEST.sha256` and the file
on disk both said `8e86df3a...` — precisely the stale-hash defect criterion 9
forbids. It was a correct and useful catch.

The cause is in this card, not the work. `python -m deckbench.skill` is declared
under `## Checks`, so compact **re-emits the artifact after the executor has
already written the report**. Any hash the executor records before that check
runs can therefore be stale by the time the run finishes, through no error of
its own. Verified separately that re-emission is deterministic — two
consecutive runs both produce `8e86df3a...` — so this is an ordering problem,
not instability.

The lesson generalises: a card must not both regenerate an artifact in `Checks`
and require a hash of that artifact to be written into a document during
execution. Either the regeneration belongs in the executor's own work, or the
hash must be written by a step that runs after it.

**A section 7 item closes with it.** The phase-1 report flags 15,680 rows
carrying a non-modal deck size as uncharacterised. Measured: 13,424 of them are
41-card decks, 5.55 percent of all rows, which is an ordinary Limited choice
rather than an anomaly. Everything from 42 upward is 2,256 rows, 0.93 percent,
and 60-card decks number five. The item should be recorded as closed so it is
not reopened.
